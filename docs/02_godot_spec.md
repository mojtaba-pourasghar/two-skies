# مشخصات Godot

> **تغییر مصوب (۱۴۰۵/۰۸/۱۴، D-ART-09):** بازی به **RPG اکتشافی سه‌چهارمی با نبرد نوبتی و نقشهٔ قابل‌راه‌رفتن** تبدیل شد (الگوی ساختاری بازی‌های سه‌چهارمی نوع Sea of Stars؛ بدون کپی محتوا). هر جا این سند «پلتفرمر معمایی دقیق به سبک Super Meat Boy»، «مرگ بی‌نهایت»، «بدون نبرد نوبتی» یا «باس با الگوی زنده» می‌گوید، با `docs/08_rpg_battle_and_overworld.md` جایگزین می‌شود. برای v1 همهٔ مرحله‌ها `topdown`اند.

این تب برای موتور Godot و برنامه‌نویس (یا Claude Code) نوشته شده است: هر عنصر بازی با نام، پارامتر، حالت و رویداد مشخص شده تا بدون حدس‌زدن ساخته شود. زبان کد GDScript و نسخه‌ی هدف Godot 4 است.

## ۱. راه‌اندازی پروژه و ساختار پوشه‌ها

- موتور: Godot 4.5، زبان GDScript، رندر Mobile (Compatibility اگر روی گوشی‌های ضعیف مشکل بود).
- جهت صفحه: افقی (Landscape) قفل. اندازه‌ی ویوپورت پایه ۴۸۰×۲۷۰، Stretch Mode = canvas\_items، Aspect = keep، Scale Mode = integer، فیلتر بافت = Nearest، Snap 2D Transforms to Pixel = روشن.
- فیزیک: ۶۰ بار در ثانیه (physics\_ticks\_per\_second = 60). تمام ثابت‌های حرکتی بر حسب پیکسل و ثانیه‌اند.
- لایه‌های فیزیک: ۱ زمین، ۲ کایرو، ۳ ایلارا، ۴ دشمن، ۵ خطر (خار/لیزر)، ۶ آیتم، ۷ ماشه (Trigger)، ۸ ابزارها و پرتابه‌ها.
- Autoload (به همین ترتیب): GameState (پیشرفت و ذخیره)، Settings، Audio، Ads (AdProvider)، Billing، NetService، SceneRouter.
- ساختار پوشه‌ها:

## ۲. ورودی و کنترل لمسی

- نگاشت InputMap: move\_left، move\_right، move\_up، move\_down، jump، action، companion، pause.
- چیدمان دکمه‌ها (نمای کناری): چپ پایین دو دکمه‌ی دایره‌ای چپ/راست (قطر ۴۸ پیکسل مجازی، فاصله ۸)، راست پایین دکمه‌ی پرش (بزرگ، ۵۶) و دکمه‌ی عمل (۴۸) و بالای آن دکمه‌ی همراه (۳۶). بالا راست دکمه‌ی توقف (۲۴). اندازه‌ها و جابه‌جایی در تنظیمات قابل تغییر است (مقیاس ۰٫۸ تا ۱٫۳).
- نمای سه‌چهارم: جوی‌استیک شناور در نیمه‌ی چپ صفحه؛ اولین لمس هر جای نیمه‌ی چپ مرکز جوی‌استیک می‌شود، شعاع ۳۲، ناحیه‌ی مرده ۰٫۲.
- چندلمسی: حداقل ۴ لمس هم‌زمان؛ هر دکمه با شناسه‌ی index مربوط به خودش دنبال می‌شود تا کشیدن انگشت از دکمه‌ای به دکمه‌ی دیگر خطا ندهد.
- بافر ورودی: پرش ۰٫۱۲ ثانیه جلوتر ثبت می‌شود؛ رها کردن پرش در هوا ارتفاع را کم می‌کند (پرش متغیر).
- لرزش (Haptic): ضربه‌ی کوتاه ۱۵ms برای فرود سخت، ۴۰ms برای مرگ؛ در تنظیمات قابل خاموش است.
- نکته‌ی پذیرش: تأخیر لمس تا واکنش کاراکتر حداکثر ۲ فریم (۳۳ms).

## ۳. فیزیک و حرکت: ثابت‌ها (نمای کناری)

همه‌ی اعداد در یک فایل `res://actors/kairo/constants.gd` به صورت const نگه‌داری شوند تا بعداً تنظیم شوند.

```
TILE = 16
GRAVITY = 900            # px/s²
FALL_GRAVITY_MULT = 1.25 # سقوط کمی تندتر
MAX_FALL = 360           # px/s
RUN_SPEED = 120
GROUND_ACCEL = 900
GROUND_DECEL = 1200
AIR_ACCEL = 700
AIR_DECEL = 500
JUMP_VELOCITY = -306     # ارتفاع ≈ 52px ≈ 3٫25 تایل
JUMP_CUT = 0.45          # ضرب سرعت عمودی هنگام رها کردن پرش
COYOTE_TIME = 0.10
JUMP_BUFFER = 0.12
WALL_SLIDE_MAX = 60
WALL_JUMP_VEL = Vector2(170, -280)
WALL_JUMP_LOCK = 0.15    # قفل کنترل افقی پس از پرش دیواری
DASH_SPEED = 260
DASH_TIME = 0.18         # ≈ 47px
DASH_COOLDOWN = 0.6
DASH_CHARGES = 1         # در زمین یا دیوار شارژ می‌شود
```

- برد پرش افقی در حداکثر سرعت ≈ 82px (۵ تایل)؛ طراح مرحله نباید شکاف بیشتر از ۴٫۵ تایل بدون ابزار بگذارد.
- مرگ فوری است (بدون انیمیشن طولانی)، شمارنده‌ی مرگ بالای صفحه، شروع دوباره در همان اتاق در کمتر از ۰٫۴ ثانیه.
- استفاده از CharacterBody2D با `move_and_slide()`؛ زمین‌های لغزنده با ضریب ۰٫۳ برای شتاب.

## ۴. ماشین حالت کایرو

حالت‌ها (enum State): IDLE، RUN، JUMP، FALL، WALL\_SLIDE، DASH، HACK، GRAPPLE، DEAD، CUTSCENE.

```
IDLE  → RUN        : |input_x| > 0
RUN   → IDLE       : input_x == 0 و سرعت < 5
IDLE/RUN → JUMP    : jump (یا بافر) و (روی زمین یا coyote)
JUMP  → FALL       : vy >= 0
FALL/JUMP → WALL_SLIDE : برخورد با دیوار و حرکت به سمت دیوار و vy > 0
WALL_SLIDE → JUMP  : jump → WALL_JUMP_VEL به سمت مخالف دیوار، قفل افقی ۰٫۱۵s
هر حالت هوایی → DASH : action (اگر ابزار دش باز است و شارژ دارد)
DASH  → FALL       : پایان DASH_TIME (گرانش در دش صفر)
هر حالت → DEAD     : برخورد با خطر یا خروج از اتاق از پایین
DEAD  → (شروع دوباره) پس از RESPAWN_TIME
```

- انیمیشن‌ها: idle(4 فریم)، run(8)، jump(2)، fall(2)، wall(2)، dash(3)، death(6)، hack(4) با نرخ ۱۰ فریم در ثانیه (دویدن ۱۲).
- ذرات: گرد و غبار هنگام فرود و تغییر جهت، رد کوتاه هنگام دش، جرقه هنگام مرگ.
- صدا: هر ورود به حالت یک رویداد صدا دارد (بخش ۱۴).
- کایرو نمی‌تواند هنگام DEAD ورودی بگیرد؛ ورودی بافر شده پس از شروع دوباره پاک می‌شود.

## ۵. ایلارا و همراهان دنبال‌کننده

- ایلارا یک CharacterBody2D مستقل با همان فیزیک کایرو است، اما با ثابت‌های خودش: RUN\_SPEED = 105، JUMP\_VELOCITY = -290، بدون دش و بدون پرش دیواری (در فصل ۱). ابزارهای او با رشد داستان باز می‌شوند.
- دنبال‌کردن: موقعیت کایرو در هر فریم در یک صف (Queue) ذخیره می‌شود؛ ایلارا با تأخیر ۰٫۸ ثانیه (۴۸ فریم) همان مسیر و همان ورودی‌های پرش را بازپخش می‌کند. اگر فاصله‌ی افقی از ۱۲ تایل بیشتر شود یا ایلارا گیر کند (۲ ثانیه بدون پیشرفت)، کنار کایرو ظاهر می‌شود (teleport) با افکت ذره.
- دستور «بمان» (نگه‌داشتن دکمه‌ی همراه ۰٫۳ ثانیه): ایلارا همان‌جا می‌ایستد و آیکون ⏸ بالای سرش می‌آید؛ «بیا» (یک ضربه): دوباره دنبال می‌کند. در حالت بمان، سپر محافظ ندارد.
- مرگ ایلارا = شکست مرحله: مرحله از ابتدا شروع می‌شود (قانون همراه). استثنا: مرحله‌ی ۷ نقطه‌ی ذخیره دارد. کایرو باید مراقب او باشد؛ ایلارا خودش خطر را تشخیص نمی‌دهد و از لبه نمی‌پرد مگر مسیر کایرو را بازپخش کند.
- هم‌پوشانی: دشمنان به ایلارا هم آسیب می‌زنند؛ جعبه‌ی آسیب او ۱۰×۱۴ است و ۱ جان دارد.
- همراهان دیگر (در نسخه‌ی اول فقط Lumi): Lumi یک Node2D شناور است که حول ایلارا با دایره‌ی شعاع ۱۸ می‌چرخد، نور PointLight2D با شعاع ۶۴ دارد، در مناطق تاریک مسیر را روشن می‌کند و با فشردن دکمه‌ی همراه پرتو روشن‌تر (شعاع ۱۱۰ برای ۲ ثانیه، خنک‌شدن ۶ ثانیه) می‌دهد.

## ۶. ابزارها: رفتار دقیق

هر ابزار یک کلاس با متدهای can\_use()، use()، update(delta) و سیگنال‌های used و ready است. ابزارها با دکمه‌ی عمل (action) فعال می‌شوند؛ ابزار فعال را بازیکن از نوار پایین ابزارها عوض می‌کند.

- ماژول هک (کایرو، مرحله ۲): در برد ۴۸ پیکسل، نزدیک‌ترین هدف قابل‌هک انتخاب می‌شود؛ نگه‌داشتن action به مدت ۰٫۶ ثانیه (نوار پر می‌شود) و در این مدت کایرو ثابت است. نتیجه: در/دکل/ربات ضعیف تغییر حالت می‌دهد. خنک‌شدن ۱ ثانیه.
- دش (کایرو، مرحله ۳): ثابت‌های بخش ۳. در دش، آسیب بعضی لیزرهای کم‌انرژی را رد می‌کند (iframes ۰٫۱۸ ثانیه فقط برای لیزر نوع کم).
- پرش دیواری (کایرو، مرحله ۲ آموزش): نیازی به دکمه ندارد؛ دکمه‌ی پرش روی دیوار.
- EMP (کایرو، فصل ۲ به بعد): شعاع ۴۸، ربات‌های ضعیف را ۳ ثانیه خاموش می‌کند، خنک‌شدن ۸ ثانیه، یک شارژ.
- گرپل (کایرو، فصل ۳): پرتاب قلاب با لمس هدف؛ برد ۹۶ پیکسل، سرعت کشش ۲۰۰ px/s.
- تیر دانه (ایلارا): پرتابه با سرعت ۲۴۰ و گرانش ۳۰۰؛ روی خاک مناسب گیاه/نردبان‌پیچک می‌رویاند (۴ تایل بلند در ۱ ثانیه). حداکثر ۳ دانه در یک اتاق.
- پمپ آب (ایلارا): روشن‌کردن چشمه/جریان به مدت ۱۰ ثانیه؛ گیاهان و موتورها را فعال می‌کند.
- شکننده‌ساز بلور (ایلارا): نگه‌داشتن ۰٫۸ ثانیه روی بلور ترک‌دار و شکستن آن؛ آسیب به ایلارا ندارد.
- سُر خوردن (Glide) (ایلارا): نگه‌داشتن پرش در هوا؛ سرعت سقوط حداکثر ۴۰ px/s، حداکثر ۲ ثانیه در هر پرواز.
- برای هر ابزار: آیکون، افکت ذره، صدا و متن توضیح در data/items.json ثبت می‌شود؛ ابزار تا باز نشده در منو خاکستری است.
- در نسخه‌ی اول (مراحل ۱ تا ۳ فصل ۱) فقط این‌ها فعال‌اند: دویدن/پرش، پرش دیواری، ماژول هک، دش ساده (در مرحله‌ی ۳)، و فرمان بمان/بیا برای ایلارا.

## ۷. موانع و دشمن‌ها: پارامترها (نسخه‌ی اول)

هر مانع یک صحنه‌ی مستقل با Area2D خطر روی لایه‌ی ۵ است. هر خطر در گروه "hazard" قرار می‌گیرد و هنگام برخورد با کایرو یا ایلارا die() آن‌ها را صدا می‌زند.

- خار (نماد ^): جعبه‌ی ۱۶×۸ در پایین تایل؛ کشنده در تماس؛ فقط وقتی آسیب می‌زند که بازیکن از بالا یا کنار با آن تماس بگیرد.
- پلتفرم شکننده (نماد \~): ۱۶×۸؛ ۰٫۳ ثانیه بعد از اولین تماس لرزش می‌کند، ۰٫۵ ثانیه بعد می‌افتد و ۲ ثانیه بعد دوباره ظاهر می‌شود.
- لیزر (نماد L): بازوی لیزر ثابت با پرتو عمودی/افقی به طول تا برخورد با دیوار؛ چرخه: ۱٫۲ ثانیه روشن / ۱٫۲ ثانیه خاموش، با ۰٫۴ ثانیه هشدار چشمک‌زن پیش از روشن‌شدن. پیش‌فرض شروع روشن با تأخیر فاز (phase) از داده‌ی مرحله.
- پهپاد گشت (نماد n): سرعت ۴۰ px/s، حرکت بین دو نقطه با محور افقی؛ لمس کشنده؛ با ماژول هک (۰٫۶ ثانیه) ۳ ثانیه خاموش می‌شود و می‌توان روی آن ایستاد؛ پس از ۳ ثانیه به گشت برمی‌گردد. چرخش جهت با ۰٫۲ ثانیه مکث.
- دیوار برقی (مرحله ۲): خاموش‌شدنی با هک؛ ۲ ثانیه خاموش.
- در/دروازه (G) و قفل دیجیتال (T): پیش از باز شدن مانع جامد؛ پس از هک، انیمیشن ۰٫۵ ثانیه باز می‌شود.
- سقف و دیوار اتاق یک محافظ دارند: خروج از پایین اتاق مرگ است (کف همیشه جامد به‌جز چاه‌های طراحی‌شده).
- یادداشت‌ها (B): تابلوی آموزشی که با نزدیک‌شدن (۳۲ پیکسل) متن کوتاه نشان می‌دهد.

## ۸. اقلام، دروازه‌ها و رویدادها

- سکه (o): ۱ سکه، مغناطیس شعاع ۱۲ برای جمع‌کردن، جمع‌شدن در همان اتاق ثبت می‌شود و فقط پس از رسیدن به نقطه‌ی خروج یا چک‌پوینت در ذخیره قطعی می‌شود. در مرگ، سکه‌های جمع‌شده‌ی اتاق دوباره ظاهر می‌شوند.
- الماس/گوهر (اعداد ۱ و ۲ و ۳ در نقشه): سه گوهر پنهان در هر مرحله (برای مرحله‌ی ۱ و ۲ و ۳ در جدول هدف‌ها). نمادهای 1/2/3 در نقشه‌ی اتاق، شماره‌ی خود گوهر یا صفحه‌ی یادداشت را نشان می‌دهند (بسته به id در داده‌ی مرحله). مقدار گوهر ثابت است، نه تصادفی.
- صفحه‌ی یادداشت (page): جمع‌آوری در متن‌های داستان؛ ذخیره در GameState.pages.
- چک‌پوینت (X در مرحله‌ی ۷ فصل‌ها؛ در مرحله‌های اولیه X نقطه‌ی خروج است): لمس آن موقعیت شروع مجدد را ذخیره می‌کند.
- نقطه‌ی خروج (X): ماشه‌ی Area2D؛ با رسیدن هر دو شخصیت (در مرحله‌های دونفره) فعال می‌شود: انیمیشن، نتیجه‌ی مرحله (سکه‌ها، گوهرها، زمان، تعداد مرگ‌ها) و ذخیره.
- رتبه‌بندی مرحله: ستاره‌ها بر اساس (۱) رسیدن، (۲) جمع هر سه گوهر، (۳) زمان کمتر از زمان هدف. مرگ هم در رتبه‌بندی شمرده نمی‌شود ولی نمایش داده می‌شود.
- رویدادها: سیگنال‌های Global برای رویدادهای مهم: level\_started، room\_entered، coin\_collected، gem\_collected، player\_died، level\_completed، companion\_command. همه از طریق یک EventBus autoload منتشر می‌شوند و در آمار (بخش ۱۶) ثبت می‌شوند.

## ۹. دوربین

- یک Camera2D با position\_smoothing\_enabled = false در نمای کناری مرحله‌های دقیق (دوربین با هر اتاق قفل می‌شود: اتاق ۳۰×۱۷ تایل = ۴۸۰×۲۷۰؛ دوربین ثابت و بدون لرزش).
- در نمای کناری مرحله‌های پیمایشی (اتاق بزرگ‌تر از صفحه): دنبال‌کردن کایرو با نرمی ۸ (`position_smoothing_speed = 8`)، محدود به مرز اتاق (limit\_left/right/top/bottom) و جلوتر از کایرو ۲۴ پیکسل در جهت حرکت (look-ahead).
- سه سطح زوم: نزدیک ۳۲۰×۱۸۰ (۱٫۵×)، استاندارد ۴۸۰×۲۷۰ (۱×)، دور ۶۴۰×۳۶۰ (۰٫۷۵×)؛ تغییر با ماشه‌ی Area2D در طی ۰٫۶ ثانیه (tween) و همیشه روی ضریب‌های سازگار با پیکسل‌سازی گرد می‌شود.
- تقسیم صفحه‌ی مورب برای مرحله‌های ترکیبی (دو شخصیت در دو جهان): دو SubViewport که با یک ماسک مورب ترکیب می‌شوند؛ در نسخه‌ی اول فقط برای صحنه‌ی ورود مرحله‌ی ۳ استفاده می‌شود یا کنار گذاشته می‌شود و برای نسخه‌ی بعد می‌ماند.

- پارالاکس: ParallaxBackground با ۳ لایه (ضرایب ۰٫۲، ۰٫۴، ۰٫۶)؛ همه‌ی موقعیت‌ها به پیکسل صحیح گرد می‌شوند.

## ۱۰. قالب داده‌ی مرحله

هر مرحله یک فایل JSON در `res://levels/data/` است (مثلاً `ch1_l1.json`) و چند اتاق دارد. هر اتاق ۳۰ ستون × ۱۷ سطر است و با کاراکتر نشانه نوشته می‌شود. `level_loader.gd` این داده را به TileMapLayer + شیءهای صحنه تبدیل می‌کند.

## ۱۲. ذخیره و داده‌ها

- ذخیره محلی در `user://save.json` با یک نسخه‌ی پشتیبان `save.bak`؛ نوشتن ابتدا در فایل موقت و سپس rename تا در صورت قطع برق خراب نشود.
- محتوای فایل: `version`، `coins`، `gems`، `levels` (به ازای هر مرحله: stars، best\_time، deaths، gems\_found، coins\_best)، `pages`، `tools_unlocked`، `daily` (تاریخ آخرین دریافت، رشته)، `settings`، `purchases`، `ads_stats`، `nexa_balance` (مخفی، در نسخه‌ی اول صفر).
- ذخیره در این لحظه‌ها: پایان مرحله، چک‌پوینت، خرید/هدیه، تغییر تنظیمات، خروج از برنامه (NOTIFICATION\_APPLICATION\_PAUSED).
- امنیت: منتداول‌شدن سکه و الماس با یک امضای HMAC ساده روی فایل محافظت می‌شود (دفاع در برابر دستکاری ساده؛ بین خریدهای پولی باید با پازخریدی بازکنی از بازار تطابق داده شود).
- نسخه‌بندی: هر تغییر قالب، version را بالا می‌برد و migrate(from\_version) دارد؛ هرگز فیلد پاک نمی‌شود.
- نسخه‌ی اول سرور ندارد؛ NetService در حالت local متدها را بی‌اثر برمی‌گرداند (جایگزینی بعدی برای بازی با امتیازهای ترتیبی).

## ۱۳. رابط کاربری: صحنه‌ها و جریان‌ها

- صحنه‌ها (همه Control با ساختار Container و Theme مشترک): `splash`، `main_menu`، `world_map`، `level_intro`، `game_hud`، `pause`، `result`، `shop`، `settings`، `letters`، `about`.
- جریان: splash ← main\_menu ←→ (play → world\_map → level\_intro → game → result → world\_map | shop | settings | letters).
- جهت نوشتار: راست‌به‌چپ (RTL) برای فارسی؛ فونت پکسلی فارسی با شکل‌دهی حروف (TextServer Advanced) فعال باشد. اعداد فارسی با تابع تبدیل نمایش داده می‌شوند.
- HUD درون مرحله: بالا چپ سکه، بالا وسط شمارنده‌ی مرگ، بالا راست توقف؛ میانه‌ی پایین نمایش ابزار فعال.
- همه‌ی صفحه‌ها با دکمه‌ی بازگشت اندروید هماهنگ‌اند (بازگشت یک مرحله به عقب، در منوی اصلی تأیید خروج).
- نشانه‌گذاری نمایشی و انیمیشن منوها طبق تب کتاب هنر («منو و راهبری»)؛ زمان هر جابه‌جایی صفحه ۰٫۲۵ ثانیه با اسلاید افقی.
- دکمه‌ها: حداقل اندازه‌ی لمس ۴۸×۴۸ پیکسل مجازی.

## ۱۴. صدا: باس‌ها و فهرست نسخه‌ی اول

- باس‌های Audio: Master، Music، SFX، UI، Ambience؛ کنترل حجم هر باس در تنظیمات. استفاده از یک AudioStreamPlayer در autoload با استخر (pool) ۸ پخش‌کننده برای SFX.
- قالب فایل: SFX با قالب OGG، ۴۴٫۱kHz، مونو؛ موسیقی با OGG لوپ‌شده. همه رویدادها با کلید (مثلاً `kairo_jump`) در یک دیکشنری در `data/sfx.json` ثبت می‌شوند.
- فهرست اول (حدود ۱۲۰ صدا، شرح کامل در تب «کتاب هنر و صدا»): حرکت کایرو (۱۸)، ایلارا و Lumi (۱۰)، خطرها (۱۸)، دشمن (۱۲)، اقلام (۱۰)، محیط (۱۴)، رابط (۱۸)، موسیقی (۶ آهنگ: منو، خانه، خیابان، سالن، پیروزی، داستان).
- تغییر آهنگ: همه‌ی ۶ آهنگ با کراس‌فید ۰٫۸ ثانیه؛ هنگام مرگ موسیقی قطع نمی‌شود (مهم‌ترین نکته‌ی حس میت‌بوی)؛ صدای مرگ کوتاه و بی‌آزار.
- اگر صدای واقعی هنوز نیست، پاهدانی قرار می‌گیرد: همه‌ی کلیدها به یک فایل بی‌صدا اشاره می‌کنند تا بازی بدون خطا اجرا شود.

## ۱۵. تبلیغات و پرداخت: ادیوری و پولاکی

- لایه‌ی انتزاع: autoload `ads.gd` با متدهای prepare(placement)، is\_loaded(placement)، show(placement) و سیگنال‌های rewarded\_completed، rewarded\_closed، failed. دو پیاده‌سازی: AdiveryProvider (اندروید) و StubProvider (محیط توسعه/ویندوز: پاسخ موفق بعد از ۲ ثانیه).
- ادیوری: کتابخانه‌ی `com.adivery:sdk` (نسخه‌ی مورد استفاده ۴٫۸٫۸) از طریق یک پلاگین سفارشی Kotlin به نام AdiveryGodot (Android Library) به گودو متصل می‌شود. کلید APP\_ID و شناسه‌ی جایگاه‌ها در `data/ads_config.json` (نه در کد) نگهداری می‌شوند.
- جایگاه‌ها: `rewarded_double_coins` (دو برابر کردن سکه‌ی پایان مرحله)، `rewarded_hint` (راهنما)، `rewarded_revive_check` (برای نجات در مرحله‌ی ۷)، `rewarded_daily_bonus`. همه‌ی تبلیغات اختیاری هستند و هیچ تبلیغ اجباری وجود ندارد.
- رفتار: قبل از نمایش دکمه‌ی تبلیغ، is\_loaded چک می‌شود؛ اگر آماده نباشد، دکمه خاکستری است و پیام «فعلاً تبلیغی آماده نیست» نمایش داده می‌شود. پاداش فقط در سیگنال rewarded\_completed داده می‌شود. فاصله‌ی حداقل ۹۰ ثانیه بین دو تبلیغ.
- پولاکی (Poolakey): پلاگین godot-poolakey (MIT) برای Godot 4.2–۴٫۵؛ متدها: connect، query\_products، purchase(sku)، consume(token)، restore. محصول‌ها در `data/shop.json` با sku، نام، مقدار و قیمت تومان (صرفاً نمایشی؛ قیمت واقعی از بازار می‌آید). مصرف‌شدنی‌ها (الماس) بعد از تحویل consume می‌شوند؛ دائمی‌ها (حذف تبلیغ) در بازی بازیابی می‌شوند.
- شرایط: کلید RSA بازار را فقط به محصول نهایی وصل کنید؛ همه‌ی متن‌های خرید باید قیمت و مقدار را شفاف نشان بدهند. ساخت اندروید: Gradle build با امضای رلیز (keystore) و بتای سفارشی؛ minSdk ۲۴، targetSdk به‌روزترین مورد قبول بازار.

## ۱۶. آمار، عملکرد و آزمون پذیرش

- آمار (محلی، بدون ارسال خارجی در نسخه‌ی اول): هر مرحله‌ای که بیشتر از ۲۵ مرتبه می‌میرند، در تنظیمات توسعه به‌عنوان «مرحله‌ی سخت» علامت می‌خورد. رویدادهای EventBus در فایل `user://events.log` نوشته می‌شوند (در نسخه‌ی نهایی خاموش).
- عملکرد: ۶۰ فریم در ثانیه روی گوشی‌های میان‌رده (۳ GB RAM)، حجم بسته کمتر از ۱۵۰ MB، زمان بارگذاری مرحله کمتر از ۲ ثانیه، استفاده‌ی حافظه کمتر از ۳۰۰ MB.
- آزمون پذیرش (هر مورد باید به‌صورت آزمایش دستی یا خودکار تأیید شود):
  - هر ۱۲ اتاق قابل عبور است (آزمون خودکار مسیر) و همه‌ی گوهرها دسترس‌پذیرند.
  - اگر ایلارا بمیرد، مرحله از ابتدا شروع می‌شود و سکه‌ها بازنشانی می‌شوند.
  - رفتن به محیط از درگاه چپ/راست دقیقاً به اتاق درست می‌رسد.
  - هیچ تبلیغ یا خریدی بدون اختیار کاربر نمایش داده نمی‌شود.
  - حالت بدون اینترنت: بازی بدون خطا اجرا می‌شود؛ دکمه‌های تبلیغ/خرید غیرفعال می‌شوند.
  - چرخش صفحه، قطع تماس و بستن برنامه با اندروید در میانه‌ی مرحله: بازگشت به همان اتاق با توقف خودکار.
  - تمام متن‌های فارسی بدون بریدگی و با جهت صحیح نمایش داده می‌شوند.

## ۱۸. سیستم فیلم‌نامه (Cutscene) مطابق تب «فیلم‌نامه»

هر صحنه یک فایل `res://data/cutscenes/c<فصل>_l<مرحله>.json` است که لیستی از نماهاست. Autoload `Cutscene` آن را خطبه‌خط اجرا می‌کند.

```json
{
  "id": "c3_l2",
  "shots": [
    {
      "code": "ن",
      "transition_in": "dissolve",
      "duration": 4.0,
      "effects": ["shake:2", "particles:dust"],
      "sound": [{"tag": "music", "id": "ch3_theme"}, {"tag": "ambient", "id": "factory_hum"}],
      "lines": [
        {"key": "c3_l2_01", "speaker": "ilara", "blip": "ilara"},
        {"key": "c3_l2_02", "speaker": "kairo", "blip": "kairo"}
      ],
      "choice": null
    }
  ]
}
```

- کد نماها به دوربین: ج = zoom 1.0 ثابت، س = 1.0 سه‌چهارم، ن = 0.75، ک = 2.0، پ = پیگیر با تاخیر ۰.۲ ثانیه، ب = 0.8 بالا-به‌پایین، ل = لرزش حداکثر ۴ پیکسل. تبدیل نما: برش، ۰.۴ ثانیه محو، ۰.۸ ثانیه سیاه، ۰.۶ ثانیه سفید، نوار سینمایی ۱۶:۹ با نوارهای ۳۲ پیکسلی.
- باکس گفت‌وگو: حداکثر ۲ خط × ۴۰ کاراکتر؛ نمایش هر حرف ۰.۰۳۵ ثانیه؛ لمس برای رد کردن نمایش حروف (فقط اگر گفت‌وگو قبلاً دیده شده باشد).
- بلیپ: هر گوینده یک صدای کوتاه دارد (`blip_<name>.ogg`) که هر ۲ حرف پخش می‌شود.
- انتخاب: فیلد `choice` کلید متن، و `effects` با کلیدهای `nexa`، `stability`، `knowledge`، `unity` در بازه‌ی ۱۰۰- تا +۱۰۰.

## ۱۹. رشته‌های فارسی (`strings_fa.json`)

- کلید هر خط: `c{فصل}_l{مرحله}_{nn}` مثل `c8_l7_03`. متن‌ها در `res://data/strings_fa.json` و کلیدی که پیدا نشود در بیلد debug با رنگ قرمز نشان داده می‌شود.
- فونت بیت‌مپ فارسی با حروف چسبیده شکل است؛ رشته‌ها قبل از نمایش با تابع `shape_fa()` شکل می‌گیرند و کاراکتر کاف عربی به کاف فارسی تبدیل می‌شود.

## ۲۰. وضعیت ذخیره برای فصل‌های جدید

```json
{

  "nexa_balance": 0,
  "stability": 50,
  "knowledge": 50,
  "unity": 50,
  "choices": {"c2_l3_a": true},
```

## ۲۱. منطق شش پایان

```gdscript
func resolve_ending(final_choice: String) -> String:
    var avg := (save.stability + save.knowledge + save.unity) / 3.0
    var strong := avg >= 70.0
    var base := {"destroy": "destruction", "stay": "coexistence", "merge": "merge"}[final_choice]
    return base + ("_strong" if strong else "_fragile")
```

- ۶ کلید پایان: `destruction_strong`، `destruction_fragile`، `coexistence_strong`، `coexistence_fragile`، `merge_strong`، `merge_fragile`؛ هر کدام یک فایل فیلم‌نامه‌ی `res://data/cutscenes/end_<key>.json`.
- نامه‌ی پدر وقتی باز می‌شود که `diary_pages.size() == تعداد کل صفحه‌ها` باشد.

## ۲۶. نقشه‌های کاشی تولیدشده‌ی فصل ۲ تا ۸

برای ۶۶ مرحله‌ی اصلی فصل ۲ تا ۸ جمعاً ۳۹۱ اتاق با مولّد خودکار ساخته شده و در فایل `tilemaps_ch2-8.zip` تحویل شده است: برای هر مرحله یک `ch{فصل}_l{مرحله}.json` و یک `all_rooms.txt` برای مرور سریع. این فایل‌ها به `res://levels/` می‌روند.

- **قالب اتاق:** ۳۰ ستون × ۱۷ سطر کامل (برخلاف قالب فشرده‌ی ۱۲ سطری فصل ۱). دهانه‌ها در سطرهای ۱۲ و ۱۳ ستون ۰ و ۲۹ هستند. فیلد `view` یکی از `side`، `topdown` یا `combined` است و `par_time` برابر تعداد اتاق‌ها × ۱۸ + ۱۰ ثانیه.
- **نمادهای پایه:** `#` جامد، `.` خالی، `o` سکه، `^` خار، `~` سکوی شکننده، `P` شروع ایلارا، `I` موقعیت کایرو، `X` خروج/ایست‌بازرسی.
- **نمادهای افزوده:** `K` کلید، `D` در، `T` قفل دیجیتال، `M` جای دشمن، `H` نقطه‌ی قلاب، `r` ناحیه‌ی طوفان، به‌علاوه‌ی نمادهای تک‌محوری هر فصل (قطعه‌ی بازیافتی، بلوک هل‌دادنی، خاک، گیاه سمی، تله‌ی پنهان، دکمه‌ی تغییر دنیا، پرس، تسمه و …). تعریف هر نماد در بخش `objects` همان فایل آمده و لودر باید نمادی را که تعریف ندارد رد کند.
- **اعتبارسنجی انجام‌شده:** برای هر اتاق یک BFS روی حالت هوا اجرا شد: پرش ۴ کاشی بالا و ۶ کاشی افقی، افتادن در چاله کشنده، قلاب با برد ۶، و در/کلید. هر ۳۹۱ اتاق از ورودی تا خروج قابل‌حل است و ۶۶ مرحله بدون خطا ساخته شد.
- **محدودیت‌ها:** این‌ها اسکلت هندسی هستند، نه طراحی دستی. مراحل ترکیبی فعلاً اتاق جانبی با در و کلید به‌جای سوییچ دو دنیا هستند. قلاب و EMP فقط تقریب زده شده‌اند. Claude Code باید با `test_solvable.gd` آن‌ها را بسنجد و در بازی‌تست دقیق‌تر کند.
